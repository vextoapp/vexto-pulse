# Vexto Pulse v2 Insights Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add weekly PageSpeed scores and daily Sentry error counts per app, shown on a private `/insights` page.

**Architecture:** A new oneshot job `dist/insights.js`, run daily by a systemd timer, pulls Sentry every run and PageSpeed when the last run is 6+ days old, and stores results in two new SQLite tables. The existing web server gets a `/insights` route rendered from those tables plus existing uptime data. Cloudflare Access (configured in the dashboard, not code) keeps `/insights` private.

**Tech Stack:** Node 26, TypeScript (erasable only, compiled with `tsc`), `node:https`, `node:sqlite`, `node:test`. No runtime dependencies.

**Spec:** `docs/superpowers/specs/2026-11-26-v2-insights-design.md`

## Global Constraints

- Under 100 MB RSS per process. Measure with `/usr/bin/time -l node dist/insights.js` on macOS.
- No `fetch()` in production code: `node:https` only. No runtime dependencies.
- Erasable TypeScript only (no enums, namespaces, parameter properties). Imports use `.ts` extensions, as in existing files.
- Timestamps are epoch ms. Days are UTC `YYYY-MM-DD`.
- App `name` is the storage key.
- The public page `/` and `/api/status` must not change.
- Secrets come only from env: `PAGESPEED_KEY`, `SENTRY_TOKEN`, `SENTRY_ORG` (default `vexto-apps`), `SENTRY_HOST` (default `de.sentry.io`). Never log them or put them in error messages stored in the DB.
- Run `npm run build && npm test` before each commit.

## Review Focus

1. **One app's PageSpeed call fails or times out** → that app gets a row with `error` set and null scores; the other apps still get scored. (Task 2 test, Task 4 manual check)
2. **A Sentry project exists but had no errors** → shows `0`, not "not set up"; an app with no matching project shows "not set up". (Task 3 test, Task 5 test)
3. **Secrets missing** → that source is skipped with one log line, the job exits 0. (Task 4 manual check)
4. **First PageSpeed run for an app** → no ▲/▼ arrow, no crash on a missing previous row. (Task 5 test)
5. **App names with HTML characters** (`Lenny's Product Brain`) → escaped on `/insights`. (Task 6 test)

### Task 4: Insights job and its systemd units

**Files:**
- Create: `src/insights.ts`, `deploy/vexto-pulse-insights.service`, `deploy/vexto-pulse-insights.timer`
- Modify: `package.json` (script `"insights": "node --disable-warning=ExperimentalWarning dist/insights.js"`)

**Interfaces:**
- Consumes: `loadApps`, `openDb`, `runPagespeed`, `fetchSentryDaily`, `sentrySlug`
- Produces: rows in `pagespeed` and `sentry_daily`.

Behaviour of `src/insights.ts` (entry script like `checker.ts`):
- **Sentry** (if `SENTRY_TOKEN` set, else log `Sentry: skipped (no SENTRY_TOKEN)`): fetch, then for each app whose `sentrySlug(name)` is in the map, upsert every day into `sentry_daily`. Log `Sentry: <n> of <m> apps linked`. A Sentry failure logs `Sentry: failed: <message>` and does not stop PageSpeed.
- **PageSpeed** (if `PAGESPEED_KEY` set, else log skipped): run only when `SELECT max(ts) FROM pagespeed` is null or older than 6 days, or `PULSE_FORCE_PAGESPEED=1`. Apps one at a time; insert each result with the run's start `ts` right after it returns (so a crash keeps earlier results). Log `<name>: perf <p> a11y <a> bp <b> seo <s>` or `<name>: failed: <error>`.
- Exit code 0 unless the DB itself fails.

Units: copy the checker's hardening lines. Service: `Type=oneshot`, `User=pi`, `ExecStart=/usr/bin/node --disable-warning=ExperimentalWarning dist/insights.js`, `EnvironmentFile=/etc/vexto-pulse/env`, `TimeoutStartSec=60min`, `MemoryMax=100M`. Timer: `OnCalendar=*-*-* 04:30`, `Persistent=true`, `[Install] WantedBy=timers.target`.

### Task 5: Insights model and "needs attention" rules

**Files:**
- Create: `src/insights-model.ts`
- Test: `test/insights-model.test.ts` (uses `openDb(':memory:')`)

**Interfaces:**
- Consumes: tables from Tasks 2–3, `checks` table, `App`
- Produces:
  - `type InsightRow = { name: string; url: string; uptime_30d: number | null; tls_days: number | null; scores: Scores | null; previous: Scores | null; pagespeed_at: number | null; pagespeed_error: string | null; errors_7d: number | null; errors_prev_7d: number | null; reasons: string[] }`. `errors_7d === null` means "not set up" (no `sentry_daily` rows for the app).
  - `getInsights(db: DatabaseSync, apps: App[], now?: number): { generated_at: number; rows: InsightRow[] }`: rows sorted by `reasons.length > 0` first, then name. `errors_7d` = sum of days `>= today-6`, `errors_prev_7d` = days `today-13 … today-7` (UTC). Uptime 30d = same formula as `status.ts` (`sum(ok)*100.0/count(*)` over 30 days). `tls_days` = latest check's value.
  - `reasons` (exact strings, thresholds from the spec): `${n} error${n===1?'':'s'} this week` when errors_7d > 0; `Performance ${p}` when < 50; `Accessibility ${a}` when < 90; `Uptime ${u}%` (one decimal) when < 99; `Certificate expires in ${d} days` when tls_days < 14.

- [ ] **Step 1: Write failing tests:**
  - `app with no Sentry rows is "not set up"` → `errors_7d === null`, no error reason
  - `Sentry project with zero errors shows 0` → rows of `errors: 0` → `errors_7d === 0`, no reason
  - `errors split into this week and last week` → 2 errors today, 5 errors 10 days ago → `errors_7d 2`, `errors_prev_7d 5`, reason `'2 errors this week'`
  - `first PageSpeed run has no previous` → one pagespeed row → `previous === null`
  - `low scores and expiring certificate add reasons, apps needing attention sort first` → app B perf 38, app A all good → rows `[B, A]`, B reasons include `'Performance 38'`
- [ ] **Step 2: Run** `npm test` → fail.
- [ ] **Step 3: Implement** `getInsights`.
- [ ] **Step 4: Run** `npm run build && npm test` → pass.
- [ ] **Step 5: Commit** `git commit -m "Add insights model and needs-attention rules"`
